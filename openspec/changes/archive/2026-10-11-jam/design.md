# Design

## Context

See `proposal.md` — Why. Constraints that shape this design:

- The octx arm contract is one-shot: dispatch a binary, pass stdin/stdout/stderr through, propagate the exit code. Arms are not scheduled.
- Arms obtain credentials from the shared credential library (defined by the separate `credential-access` change); the head does not inject credentials into the environment.
- ListenBrainz rate-limits to roughly **one request per second**; Qobuz rate-limits independently.
- The prior `spotify-qobuz` work proved the Qobuz side end to end and supplies the match approach to preserve.

### Verified upstream behavior (probed against the live API while planning)

These facts corrected the original plan and drive the decisions below.

- **Normalizer.** The player endpoint is `POST https://listenbrainz.org/player/?recording_mbids=<csv>` — the blueprint is registered at `url_prefix='/player'`, *outside* the `/1` API prefix. The previously planned `POST /1/player/` returns 405/404 on `api.listenbrainz.org`, which also 410s `/player/`. It works **unauthenticated**, accepts at most 50 MBIDs per request, and returns `{"playlist": {"playlist": { …, "track": [ … ]}}}` (a double-wrapped JSPF). Each track carries `title`, `creator` (artist credit), `album`, `duration` (ms), an `identifier` array whose first element is `https://musicbrainz.org/recording/<mbid>`, and `extension["https://musicbrainz.org/doc/jspf#track"].additional_metadata.artists[]` with `artist_credit_name`/`artist_mbid`.
- **Normalizer is the only title+artist source.** `GET /1/metadata/recording/?recording_mbids=…` exists but returns only `name`/`length`/`isrcs`, with no artist credit, so it is not a substitute.
- **LB Radio.** The current endpoint is `GET /1/explore/lb-radio?prompt=<prompt>&mode=<easy|medium|hard>`. `prompt` is ListenBrainz's prompt language (`artist:(queen)`, `tag:(shoegaze)`, with popularity modifiers), `mode` is mandatory, and the endpoint **requires a user token**. It returns `{"payload": {"jspf": <JSPF playlist>, "feedback": [ … ]}}`, and is additionally subject to a stricter **per-token** limit of five requests per five-second window, separate from the global rate limit. The legacy `/1/lb-radio/artist/{mbid}` and `/1/lb-radio/tags` routes still respond but are superseded and require additional mandatory parameters (`max_similar_artists`, `max_recordings_per_artist`, `pop_begin`, `pop_end`); they are not targeted.
- **Collaborative-filtering recs.** `GET /1/cf/recommendation/user/{user}/recording` takes the user name in the path and serves the *precomputed* model — ListenBrainz trains it from listens an external scrobbler submits, so the arm reads a result it cannot produce. It is **publicly readable** (probed unauthenticated: `200` with a body), and accepts `count` (default 25, maximum 1000) and `offset`. The response's `payload.mbids[]` entries carry `recording_mbid`, `score`, and `latest_listened_at`, with `last_updated`, `model_id`, `model_url`, and `total_mbid_count` alongside; `GET /1/validate-token` turns a token into its user name — a request the account document can save by recording the name itself. When no model exists for the user it answers **`204 No Content`** — `No recommendations due to absence of recent listening history for user {user}`, or `No recommendations for user {user}, please try again later.` when the model is empty; an unknown user is `404`. The endpoint is marked *experimental and probably will change*. The credential names the user; it is not what authorizes the read.
- **Qobuz exposes no listening-history endpoint.** The shipped web client (`play.qobuz.com/resources/8.2.0-b034/bundle.js`, 9.2 MB) contains no `*listen*` API route at all — its entire `user/*` namespace is `user/lastUpdate`, `user/login`, and `user/settings` — and `Discover/RecentlyPlayed` is a front-end route, not an API method. The candidate `qobuz-api` v2.0.0 crate implements `auth`, `content`, `favorites`, `requests`, and `service`, and likewise no listen history. **Consequence:** "gather all recent listens from Qobuz" cannot be built against the official API, and reading the Recently Played page is excluded by the proposal's rule against browser scraping. Listen ingestion is therefore fed from outside the arm, and no Qobuz call may be introduced on the write side.
- **Qobuz publishes plays server-side, so Last.fm is the standard history source.** The shipped client's account strings include `activeScrobble` ("Enable playing scrobbling"), `activePublish` ("Enable playing publication"), `lastfm` ("Last.FM"), and `myAccounts` ("My linked accounts"), and the bundle contains **no** `audioscrobbler` host — so Qobuz links the account and pushes plays from its own servers rather than from the client. Last.fm's documented `user.getRecentTracks` (`/2.0/?method=user.getrecenttracks&user=<user>&api_key=<key>&format=json`, with `limit` up to 200, `page`, and `from`/`to` UNIX bounds) returns exactly the fields a listen needs — a `<date uts="…">` timestamp per track, artist, track name, and album. Confirmed live: the fields arrive as `artist.#text` and `album.#text`, and adding `extended=1` silently re-shapes both into objects keyed `name`, so the mapper must not request it. **Consequence:** a Qobuz history can reach `--input` as NDJSON through a documented API (`listened_at ← date.uts`, `artist`, `title`, `album`) with no scraping and no Qobuz call, and the only new secret such a converter needs is a Last.fm API key.
- **A user's listens are readable from ListenBrainz.** `GET /1/user/{user}/listens` takes `count` and answers `{"payload": {"count", "latest_listen_ts", "listens": [{"listened_at", "recording_msid", "inserted_at", "track_metadata": {"artist_name", "track_name", "release_name", "additional_info": {"recording_mbid"}}}]}}`; probed without a token, `200` for a public user. It is the only service-side way to read listens back, and the only credential-free one. Confirmed against the live API: the payload also carries `oldest_listen_ts` and `user_id`, each listen also carries its `user_name`, `track_metadata` also carries `mbid_mapping` and an `additional_info.artist_names[]` list, and `artist_name` is a single joined string (`"Drake, Rihanna"`) rather than a list. Unknown query parameters are ignored, and timestamp-bounded queries (`min_ts`, `max_ts`) failed to complete in two of two probes — so the source bounds a run with a limit and relies on listen identity for correctness rather than on a timestamp window.
- **Qobuz playlist writes.** The mutations available are `playlist/create`, `playlist/addTracks` (at most 50 ids per call, comma-joined and not percent-encoded), `playlist/deleteTracks`, and `playlist/update` (name/description only); `playlist/get` returns `tracks.items[]` when asked for `extra=tracks`, `playlist/getUserPlaylists` returns the authenticated user's playlists, and `track/search` finds a track by artist and title. There is no reorder operation. Verified against python-qobuz 0.0.2 and qobuz-dl's `qopy.py` rather than by probing, because no Qobuz credential is configured yet — the shapes are pinned by fixtures so a live probe can confirm them later.
- **Listen submission.** `POST /1/submit-listens` takes only two top-level keys per listen — `listened_at` and `track_metadata` — so the client-supplied identity travels at `track_metadata.additional_info.recording_msid`. Duplicate suppression is the database's, not the endpoint's: `INSERT INTO listen (…) ON CONFLICT (user_id, listened_at, recording_msid) DO NOTHING`, and the ingest helper returns only the rows it actually created — *"listens absent from the result were duplicates"*. `listen_type` is `single`, `import`, or `playing_now`; `single` and `playing_now` reject more than one listen per request, so **only `import` carries a batch**. The token must carry the `listenbrainz:submit-listens` scope, `listened_at` must be after 2002-10-01, and the server refuses listens from a paused user or from an account without an email when the server requires one. The success response is `{"status":"ok"}` and does **not** report how many listens were new.

## Goals / Non-Goals

**Goals:**

- A single source-agnostic pipeline: any source reduces to one normalized document, and everything downstream is shared.
- A Qobuz-free, machine-readable path (`--output json`) so recommendations can be consumed without Qobuz being reachable or configured at all.
- On-demand, parameterized invocation (`recs`, `radio`, `scrobble`, `status`) with no dependence on any ListenBrainz-generated playlist.
- A run that reads an absent or stale model fails loudly and changes nothing, so the arm can never empty a playlist because upstream had nothing to say.
- Idempotent Qobuz writes and a non-mutating preview.
- A write path that is safe to schedule: re-reading the same input never duplicates a listen, and stays correct without any bookkeeping.
- Reuse existing crates and the shared credential library rather than reimplementing credential handling.

**Non-Goals:**

- No scheduler, daemon, or timer inside the arm; no `created_for` playlists (both deferred to the caller by design).
- No built-in web UI or player; `--output json` is the integration point for one.
- No `fresh` (release-shaped, N+1 expansion) and no recommendation-feedback write-back in this change.
- No custom match-scoring engine; v1 preserves the proven behavior.
- No Spotify, no browser automation, no legacy `/1/lb-radio/*` adapters, and no runtime scrape of the Qobuz web client for app credentials.
- No on-device capture and no Android component of any kind: no app, no broadcast receiver, no notification-listener or media-session service. Capturing Qobuz plays is Last.fm's job — Qobuz pushes them from its own servers — and moving them onward is `jam scrobble`.
- No commercial use of Last.fm data, no sub-licensing it, and no copy of it published without the credit the API terms require (see Decisions).

## Decisions

**Outputs are sinks, not the pipeline's purpose.** The arm's product is a normalized *playlist document*; Qobuz is one consumer of it. *Alternative:* treat Qobuz as the terminal stage — rejected: it makes a single destination a hard dependency, forces a Qobuz credential for any use, and blocks the "view the recommendations" case the design should support.

**Two sinks, selected explicitly.** `--output json` serializes the document to stdout; `--output qobuz` resolves and syncs. `--output` is required with no default, so a bare invocation never silently writes anywhere. *Alternative:* default to `qobuz` (the original intent) — rejected by the same reasoning, a default would keep the destination coupled. `m3u` and other serializations are deferred; the JSON document is sufficient and a converter is trivial.

**Source-agnostic pipeline with one document shape.** `recs` yields recording MBIDs which are expanded through the normalizer; `radio` already returns JSPF, which is mapped into the same entry shape. Both converge on the document, so the sinks never know which source ran. *Alternative:* per-source end-to-end code — rejected: it duplicates the resolve/write path and multiplies the matcher's surface.

**`POST https://listenbrainz.org/player/` as the normalizer.** Recording MBIDs are expanded to entries in batches of at most 50. *Alternative:* `/1/metadata/recording/` per MBID — rejected: it carries no artist credit and is N+1 against a 1 req/s budget.

**The Qobuz sink is a thin client on the head's own `reqwest`; the `qobuz-api` crate was rejected by the gate it was named for.** The spike (task 2.3) asked whether that crate could serve as the sink. It cannot: **v2.0.0 has no playlist writes at all** — its playlist module is read-only (`playlist/search`, `playlist/get`) and offers no create, no track add, and no track remove, which is the whole job. It is also **GPL-3.0-or-later**, and the project has chosen no license, so shipping it inside the released arm binaries would impose copyleft obligations the project has not accepted; and it would add 46 crates to the arm, including a second `reqwest` (0.13 beside the head's 0.12), `lofty`, `rayon`, and `tracing-subscriber`. The thin client therefore adds no dependency at all: `reqwest`, `serde`, and `serde_json` are already in the arm, and the released arm is 2.2 MB stripped. *Alternative:* accept the crate and hand-roll the four playlist mutations anyway — rejected: it pays the license and size cost for a client whose useful parts would not be used.

**Qobuz's playlist API is append-only, which the sink is built around.** Verified against two independently working clients (python-qobuz 0.0.2 and qobuz-dl's `qopy.py`): the mutations are `playlist/create`, `playlist/addTracks` (at most 50 track ids per call), `playlist/deleteTracks`, and `playlist/update` (name and description only). There is **no reorder or move call, and no call that accepts a full ordered track list** — unlike the crate's premise, this is what the API does and does not offer. The app id travels as an `X-App-Id` header and stays a constant in the arm, with `accounts.<name>.qobuz.app_id` as the override; the user's `user_auth_token` travels as a query parameter. **Consequence, recorded here because the spec's ordering requirement depends on it:** with append-only mutations, "ordered by the source's ranking" and "additions applied before removals so an interrupted run cannot leave the playlist thinner" cannot both hold in general — see the decision below.

**Credentials: one document at host `jam`, one account per person.** The store is a flat host → value map, so the arm reads exactly one credential — host `jam` — and interprets its value as a JSON document: a `version`, a shared `lastfm.api_key`, an optional `default` account, and an `accounts` map whose entries carry only the fields that person's services need (`lastfm.user`; `listenbrainz.user` and `token`; `qobuz.user_auth_token`, with an optional `app_id`). `--account` selects the entry; when it is omitted the document's `default` names it, or the sole account is used, and several accounts with no default is an error that lists them rather than a guess. Reading one host keeps the store's code out of jam's schema entirely: the library neither parses nor validates the document, the arm reports failures as a path into it (`accounts.wife.listenbrainz.token`), and no value is ever printed. *Alternative:* one host per credential per person (`listenbrainz:wife`) — rejected: it imposes a naming convention on every invocation, and a scheduler typo would point her run at his account, where one document makes the account a single explicit choice with no fallback. *Alternative:* a document per account (`jam:wife`) — deferred, not rejected: hosts are opaque to the store, so that split costs no schema change if one document proves too broad. The Qobuz app id stays a constant in the arm with `accounts.<name>.qobuz.app_id` as the override, and the spike records whether the `app_secret` override is ever needed.

**v1 matcher preserves prior behavior.** Query the Qobuz catalog with artist + title and take the best acceptable hit; skip when none. MBID, album, and duration are carried through the document even though v1 does not score on them, so a later hardening pass needs no re-plumbing. *Alternative:* build the scoring engine now — rejected as speculative; `--dry-run` provides the observation needed to justify it.

**Diff-and-converge on the set, in the source's order.** The sink computes additions and removals against the target playlist's current contents and applies only those, so a repeated run with unchanged upstream data changes nothing. The playlist's order is the source's ranking rather than the order mutations happened to occur in, and additions are applied before removals so an interrupted run cannot leave the playlist thinner than it found it. jam owns the playlist: a track that is no longer recommended is removed, and a hand-added or hand-reordered track is not preserved. *Alternative:* replace the contents wholesale in one update call — deferred to the spike (2.3), not rejected: it would express the ranking directly and is idempotent by construction, and the old objection (it discards manual ordering) does not apply to a playlist jam already owns; it is used only if the API can carry the full ordered list in one call. *Alternative:* add-only — rejected: it cannot express "removed upstream", and the playlist is expected to be jam-owned. *Alternative:* keep the order the mutations produced — rejected: the source returns a ranked list, so a playlist ordered by archaeology gets worse the longer the schedule runs.

**The spike narrowed the ordering decision, and this is the part it could not settle.** "Ordered by the source's ranking" and "additions before removals" are mutually satisfiable only if the API can express order directly; the spike showed it cannot (no reorder call, no ordered replacement). The choice between the two is therefore a product decision, not an implementation detail. **It is settled in favour of crash-safety:** additions are applied first and removals second, so an interrupted run leaves extra tracks rather than missing ones. The source's ranking still fixes the order of everything a run *adds* — a fresh playlist is built in rank order — but a track already present keeps the position the API gave it, so the order of an existing playlist can drift as recommendations change. The alternative (rewrite the playlist each run to express the ranking exactly) is rejected for v1 because it opens a window in which an interruption leaves the playlist thinner than it found it, which is the failure the ordering requirement exists to prevent.

**Target playlist resolved on every run; no state file.** `--playlist` accepts a name or an id. A name is resolved through the user's playlist list on every run and created when it does not exist; the default target name is a registered constant per source, so `recs` and `radio` scheduled against one account cannot converge on the same playlist. *Alternative:* cache the name→id map in `{data_dir}/octx/jam.json` — rejected: it is a file to corrupt and a second source of truth for a fact the API answers inside a request the run is already making, and the arm is easier to reason about when every fact it needs comes from the remote it is converging on. Add the cache when a rename or a mid-write failure actually bites.

**Throttle at the pipeline, backoff at the edges.** A shared request throttle keeps ListenBrainz calls within the one-per-second guidance; HTTP 429 is retried with exponential backoff (delegated to the Qobuz crate where applicable).

**An absent source aborts; the sink never converges on an empty document.** The recommendation endpoint answers `204` when no model exists for the user — a normal state after a listening break, and the normal state before the first model is trained. Because the sink's job is to converge, the naive reading of an empty resolved set would *remove every track* from the user's playlist. A source that has nothing to give is therefore treated as a failure, not as an empty result: the arm exits non-zero before any write and explains the cause. *Alternative:* converge on whatever the source returned — rejected: it turns an upstream gap into data loss. *Alternative:* succeed silently with an empty document — rejected: it erases the difference between "nothing to recommend" and "no model yet", and it is the same conflation that makes the destructive case possible.

**`jam status` exists so that failure can be avoided, not merely reported.** The empty-source condition is common and recoverable, so the arm exposes a readiness check that reports credential presence, the account's user name (recorded in the document, or derived from the token), and the model's last-updated time, exiting `0` only when `recs` could succeed. *Alternative:* let the user discover it from a failed run — rejected: the condition is predictable, cheap to check, and the cost of not checking is a confusing error. `status` reuses the same `204`/`404` handling and writes nothing.

**The ListenBrainz token identifies the user; it does not authorize the read.** The recommendation endpoint is publicly readable — verified unauthenticated — so the arm must not assume anonymous requests fail, and must not blame a missing credential for a `404`. The account document names the user; the token only authorizes `radio` and submission. Only `radio` genuinely requires a token, and there ListenBrainz gates the endpoint against scrapers; `status` needs one only to name the user when the document does not.

**jam is bidirectional, and both directions follow one discipline.** The read side is source (`recs`, `radio`) → playlist document → sink (`json`, `qobuz`); the write side is source (`ndjson`, `lastfm`, `listenbrainz`) → listen document → sink (`listenbrainz`, `json`). Normalizing to a document in both directions is what lets a sink be added without touching a source, and what makes `--output json` a usable no-network inspector on either side. *Alternative:* two separate binaries — rejected: it would duplicate the document, throttle, credential, and reporting machinery for no separation benefit, and the two directions share a token, a host, and a rate limit.
**One account per run; scheduling is external and per person.** Each account is its own invocation (`--account wife`), so a scheduler runs one command per person and every run's exit code, summary, and sink stay attributable to a single account; the arm keeps no state between runs and carries no scheduler. *Alternative:* iterate every account inside one run — rejected: one person's failure or playlist would become indistinguishable from another's in the summary and the exit status, and the sink and target playlist differ per account anyway.

**The write side reads from sources, not only from a file.** `jam scrobble --source` selects `ndjson` (the default, with `--input`), `lastfm`, or `listenbrainz`, and each reduces to the same normalized listen document, so the sink, the batching, and the reporting stay unchanged. The two networked sources exist because the documented route out of Qobuz runs through Last.fm rather than through Qobuz, and because a user's own listens are readable back from ListenBrainz. *Alternatives:* NDJSON alone (rejected — it leaves the one standard Qobuz-to-history path unusable without a converter that octx would still have to ship and maintain); reading the Qobuz player page (rejected — browser scraping, which the proposal excludes).

**Last.fm's terms make attribution part of the data, not part of the documentation.** The Last.fm API terms require a credit and a link back on any copy of Last.fm data that is published, distributed, or communicated to the public (2.7, 4.2.1–4.2.2), forbid sub-licensing (4.3.3), cap stored data at 100 MB and require caching per the response headers (4.3.4), and permit non-commercial use only (3.1–3.2). The `lastfm` source therefore stamps a document-level attribution — naming Last.fm and linking to the scrobbling account's Last.fm page and to the API terms — and prints the same credit on stderr. *Alternative:* state the obligation only in `skill.md` — rejected: the document is the artifact that gets copied and passed on, so the credit has to travel inside it.

**A listen keeps its upstream identity when there is one.** A listen read from ListenBrainz keeps the `recording_msid` it was returned with; every other listen derives a UUIDv5 from user, listen timestamp, artist, and title. *Alternative:* always derive from the field values (rejected — re-delivering a user's own listens would invent parallel identities, so a play both scrobbled by the user's client and read back by jam would land twice). Identity is what makes the write side re-runnable with no state, so it must match what upstream already holds whenever upstream can tell us.

**Idempotency comes from a deterministic listen identity, not from local state.** Each listen's `recording_msid` is derived from the listen itself — user, timestamp, artist, title — or preserved from upstream when the source supplies one — so ListenBrainz's `ON CONFLICT … DO NOTHING` discards repeats and the arm can re-read an entire input every run with no offset, no watermark, and no state file. *Alternative:* record submitted listens locally — rejected: it adds a file to corrupt and a window to get wrong, and is strictly less reliable than the server's own uniqueness constraint. The failure mode is sharp enough to state plainly: a random or run-varying identity would never collide, so duplicates would accumulate silently and permanently.

**The submission response cannot report what it discarded.** ListenBrainz answers `{"status":"ok"}` however many listens were new, so the arm reports what it sent and what it rejected from the input — never a count of listens added, which it cannot observe. *Alternative:* read the listens back afterwards to compute a delta — rejected: an extra request every run against a one-request-per-second budget, to produce a number nobody acts on.

**Empty listen input is a no-op; an absent recommendation model is a failure.** The two conditions look alike and mean opposite things. Nothing to submit is the normal state of a scheduled run whose log has not grown; nothing to recommend means the upstream model the arm depends on does not exist yet. The read side therefore aborts, and the write side exits zero. *Alternative:* one rule for both — rejected: it would either make every quiet cron run look like a failure, or make an emptied playlist look like success.

**One ListenBrainz token per account, and it must be allowed to submit.** An account's `listenbrainz.token` serves both `recs` and `scrobble` — but reading recommendations needs no scope while submitting listens requires `listenbrainz:submit-listens` — so it must carry both. The arm must distinguish "token unknown" from "token may not submit", or a read-only token would send the user hunting for a credential they already have.

## Risks / Trade-offs

- **An upstream `204` is easy to mistake for "no recommendations"**, and with convergence that mistake is destructive → absent data is a non-zero failure before any write, with a dedicated test asserting the target playlist is left untouched.
- **The upstream paths are undocumented-in-practice and can move** — the player endpoint sits *outside* the `/1` API prefix, the legacy radio routes still answer alongside the current one, and the recommendation endpoint is labeled *experimental and probably will change* → each endpoint is isolated behind one module, the base URL is configurable for tests, and a fixture test pins each response shape so a change fails loudly rather than silently.
- **Qobuz is an undocumented, reverse-engineered API** and its app id/secret rotate → the app id is a constant with an account-level `app_id` override, so a rotation is a one-constant change rather than a broken scrape, and the Qobuz client is isolated behind one module so the constant and the override live together.
- **The matcher can silently pick a wrong track** → v1 is deliberate parity, `--dry-run` exposes matches before writing, and unresolved entries are always reported rather than guessed.
- **`qobuz-api` may be heavier than the arm budget** (it also carries download/streaming/metadata-embedding code) → the gating spike decides; the thin-client fallback is a small, known path.
- **Credential model drift** (token vs email/password) → the arm only calls the library, so changing the stored shape does not touch the arm's code.
- **Two JSPF sources with possibly different nesting** (the player endpoint double-wraps, the radio endpoint nests under `payload.jspf`) → the parser normalizes both into one entry type and both shapes are covered by fixtures.
- **Chunking bugs at the 50-MBID boundary** → chunk size is a named constant with a test at 49/50/51.
- **A random `recording_msid` would silently duplicate every listen** → the identity is derived deterministically and a test asserts that two runs over the same input derive identical identities.
- **Two genuine plays of the same track in the same second collapse into one** — the identity has second resolution and no finer tiebreaker → recorded as a known limitation rather than discovered later; a source with sub-second data would need a different identity basis.
- **A read-only ListenBrainz token fails only at submit time** → the scope failure is reported distinctly from a missing credential, so the user is not sent looking for a credential they already have.
- **The Qobuz playlist is jam-owned** → manual additions and any hand-reordering are reverted by the next run, which is inherent to a scheduled mirror and must be stated in the skill rather than discovered. `--dry-run` reports the removals before they happen.
- **The `jam` document is one credential holding every account** → a single `octx creds get jam` yields all of them, and delegating `--credential-host jam` to a child agent hands over the whole set. The document model trades per-host least privilege for one explicit selection, which is why the arm names paths and never values; narrowing to `jam:<account>` needs no store change if that trade stops being acceptable.

## Migration Plan

1. Depend on the `credential-access` change's shared library to fetch the credential for host `jam`, then parse and validate the account document in the arm.
2. Land the arm behind its own crate and `registry-index.json` entry; no existing behavior changes.
3. Rollback: uninstall the arm; it holds no credential state, so removing it leaves nothing behind.

- Whether the `feedback` array that LB Radio returns warrants a later, opt-in feedback sink. Deferred with feedback write-back.
